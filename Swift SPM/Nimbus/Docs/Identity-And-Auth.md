# Identity, Consent & Auth

How identity, login/logout, and consent actually behave with the AEP Mobile SDK — the scenarios and the questions that come up most, followed by how this app demonstrates each. If you only read one section, read [The mental model](#the-mental-model) and [Quick answers](#quick-answers).

Related: [Messaging & Personalization](Messaging-And-Personalization.md) · [SDK API Reference](Services-API.md).

## The mental model

Every device has **one anonymous identity — the ECID** — and zero or more **known identities** (email, CRM ID, phone) that can be *linked* to it. Think of it as one node (the ECID) that other identity nodes attach to over time.

- The **ECID (Experience Cloud ID)** is generated by the Edge Identity extension the **first time the SDK initializes** — on first launch, *before* any login or consent choice. It is not tied to a user.
- **Logging in doesn't create a new identity** — it *links* a known identifier (e.g. `Email`) to the same ECID.
- **Logging out doesn't reset the ECID** — it only unlinks the known identifier locally. The device stays the same device.
- Only **uninstalling the app** (or a full opt-out) produces a new ECID on the next install.

Everything below follows from this: the ECID is durable and device-scoped; known identities come and go on top of it.

## Scenario: login

Signing in **links a known identity to the current ECID**. The typical flow:

1. Build an `IdentityMap` with the identifier under a namespace (e.g. the standard `Email` namespace), mark it `authenticatedState: .authenticated`, and call `Identity.updateIdentities(with:)`.
2. This updates the **local** IdentityMap only — it does **not** call the server by itself.
3. The link reaches AEP's **identity graph** on the **next Edge event** the app sends (any `Edge.sendEvent`, a `trackAction`, a consent update, etc.), because every outgoing Edge event automatically carries the current IdentityMap.

So "log in" really means: *attach this email to my ECID, and let the next event tell the server about it.* If you need the link server-side immediately, send any Edge event right after `updateIdentities`.

### authenticatedState — what it means

Each identity item declares how sure you are of it:

| State | Meaning |
|---|---|
| `.ambiguous` | Unknown / not asserted (default) |
| `.authenticated` | The user actively authenticated this session |
| `.loggedOut` | Previously authenticated, now logged out |

Use `.authenticated` when the user just logged in; it's what downstream segmentation and identity-graph stitching rely on.

## Scenario: logout

Logging out **unlinks the known identity but keeps the ECID**:

1. Read the current IdentityMap, then call `Identity.removeIdentity(item:withNamespace:)` for each known item you want to clear (e.g. every `Email` item).
2. The ECID is untouched — the device identity is unchanged.
3. This clears only the **local** IdentityMap. The `Email ↔ ECID` link already written to the **server-side identity graph** is permanent; removing it on-device does not delete it server-side.

Because the graph link is permanent, a **future login from the same device re-stitches the same graph** — the user's history reconnects. Logout is a client-side "stop asserting this identity," not a server-side erasure. (Erasure is a separate privacy/GDPR flow.)

## Scenario: guest / anonymous

Continuing as a guest links **nothing** — the user stays anonymous on the existing ECID. This matters: **personalization and messaging still work for anonymous users**, because they key off the ECID, not a login. Guests get offers, content cards, in-app messages, and push all the same. Login is an *enrichment* (known identity, cross-device stitching), never a prerequisite for the SDK to function.

## Identity graph vs. Profile attributes (the #1 confusion)

Putting an email in the IdentityMap does **not** put it in the profile's attributes. They are two different systems:

| | IdentityMap (`updateIdentities`) | Profile attributes |
|---|---|---|
| Purpose | **Stitch** this device/ECID to a known identity | **Store** data about the person (name, email, tier) |
| Lands in | Identity graph | Real-Time Customer Profile record |
| How to write | `Identity.updateIdentities` | XDM fields in an `Edge.sendEvent` (e.g. `personalEmail.address`, `person.name`) |

So if you linked an email via `updateIdentities` and it doesn't appear as a profile *attribute* — that's expected. To populate attributes, send them as XDM in an Edge event (and the schema/field group must carry those fields, with Profile enabled on the schema + dataset).

## Standard vs. custom namespaces (why "search by email" fails)

The AEP Profile / Identity Graph viewer only lets you look up by **standard** namespaces (`Email`, `Phone`, `ECID`, `IDFA`, …) or namespaces explicitly configured as searchable.

- Store email under the **standard `Email` namespace** → searchable in the Profile viewer.
- Store it under a **custom namespace** (e.g. `CRM ID`) → not searchable "by email"; you'd search by that custom namespace's value instead.

A common setup links **both**: `Email` (standard, searchable) and a custom `CRM ID` (your system's key). The identity graph ties them to the same ECID.

## Scenario: consent

Consent governs whether data collection is allowed. Three app-side states map to the Edge Consent XDM payload:

| State | Sent to Edge? | Effect |
|---|---|---|
| `pending` | **No** | The **tag property's default consent** governs until the user chooses |
| `yes` | `collect.val = y` | Collection allowed |
| `no` | `collect.val = n` | Collection disallowed |

Two things trip people up:

- **Consent updates hit the server *immediately*.** Unlike `updateIdentities` (local until the next event), `Consent.update` fires a `consent.update` Edge event right away. Legally, the choice must be recorded before further collection — so it can't wait for a later event.
- **Declining consent doesn't delete the ECID.** The ECID still exists on-device; what changes is whether events are collected downstream, per your datastream/consent config. If your tag property's default consent is `pending`/`yes`, events may still flow until the user actively declines.

## Persisting the gate ("don't ask twice")

"Has the user chosen consent / seen login?" is UI state, and it must **survive a cold launch** or the one-time primer isn't one-time. Two options:

1. **Persist a local flag** (e.g. UserDefaults) — simplest, unambiguous.
2. **Derive from the SDK** — read the stored consent value back at launch and treat "not pending" as "already chosen." Cleaner (SDK as source of truth) but depends on your tag property's default being `pending`, otherwise you can't distinguish "user chose" from "default."

A subtle bug if you skip this: the primer reappears on every relaunch **and** re-sends `consent.update` each time.

## Quick answers

| Question | Answer |
|---|---|
| Does logging in change my ECID? | No. Login links a known identity to the same ECID. |
| Does logging out reset the ECID? | No. Only uninstall / opt-out yields a new ECID. |
| Does `updateIdentities` call the server? | No — local only, until the next Edge event carries the map. |
| I linked an email but can't see it in Profile attributes — why? | IdentityMap ≠ profile attributes. Send XDM fields via `Edge.sendEvent` to populate attributes. |
| I can't search a profile by email — why? | Use the standard `Email` namespace; custom namespaces aren't searchable "by email." |
| Do offers / messages work for guests? | Yes — they key off the ECID, not login. |
| Does declining consent delete the ECID? | No. It affects downstream collection, not the on-device ECID. |
| Does consent go to the server immediately? | Yes — `Consent.update` fires an Edge event right away (unlike identity). |
| Why does my consent primer show every launch? | The "chosen" flag isn't persisted across cold launches. Persist it, or derive from the SDK. |

## How this app demonstrates it

The app keeps every SDK call behind a protocol (`IdentityService`, `ConsentService`) so the flows above are easy to follow in one place.

- **Launch gate** — [`RootView`](../Nimbus/App/RootView.swift) shows Consent → Login → main tabs, each shown once (flags persisted in [`AppEnvironment`](../Nimbus/App/AppEnvironment.swift) so they survive cold launch).
- **Login** links an `Email` item (`.authenticated`, primary) — [`AEPEdgeIdentityService.login`](../Nimbus/AEPIntegration/Identity/AEPEdgeIdentityService.swift).
- **Logout** removes every `Email` item, keeps the ECID — [`AEPEdgeIdentityService.logout`](../Nimbus/AEPIntegration/Identity/AEPEdgeIdentityService.swift). The user returns to the tabs as a guest, not to the login screen.
- **Guest** links nothing — [`AppEnvironment.continueAsGuest`](../Nimbus/App/AppEnvironment.swift).
- **Consent** maps the three states to the XDM payload and never sends `pending` — [`AEPEdgeConsentService`](../Nimbus/AEPIntegration/Consent/AEPEdgeConsentService.swift).
- **ECID** is read once at launch and shown in Login/Profile — [`AEPEdgeIdentityService.experienceCloudId`](../Nimbus/AEPIntegration/Identity/AEPEdgeIdentityService.swift).

The login here is a local, unauthenticated demo (no backend auth) — its only job is to exercise identity linking, not to model a real auth system.
